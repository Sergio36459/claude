# Этап 3. Архитектура системы

## 1. Общая схема

```
                        ┌─────────────────────────────────────────────┐
                        │                   CDN                       │
                        │  статика Next.js · дневные бандлы · PMTiles │
                        └───────┬──────────────────────┬──────────────┘
                                │ (95% запросов)       │
┌──────────────┐        ┌───────▼────────┐     ┌───────▼────────┐
│   Браузер    │◄──────►│  Next.js (web) │     │ Object Storage │
│ MapLibre GL  │        │  SSR/ISR, OG   │     │  /data/**      │
└──────┬───────┘        └───────┬────────┘     └───────▲────────┘
       │ поиск, фильтры,        │                      │ publish
       │ сложные запросы        │                      │
┌──────▼─────────────────────────▼──────┐      ┌───────┴────────┐
│         NestJS API (api)              │      │  ETL (etl)     │
│  REST /api/v1 · Redis cache · zod DTO │◄─────┤  импорт·сверка │
└──────────────────┬────────────────────┘      │  ·публикация   │
                   │ Prisma + raw SQL (PostGIS)└───────┬────────┘
          ┌────────▼─────────┐                         │
          │ PostgreSQL 16 +  │◄────────────────────────┘
          │ PostGIS 3.4      │   источники: ISW, ACLED, Oryx,
          └──────────────────┘   DeepState, официальные сводки
```

Принцип: **чтение — со статики, запись — через ETL, API — для динамики** (поиск, произвольные фильтры, экспорт, админка).

## 3. Frontend-архитектура

### 3.1. Состояние

- **Zustand** — синхронное UI-состояние: `currentDate`, `playback {isPlaying, speed}`, `activeLayers`, `theme`, `filters`. Слайсы мелкие, селекторы точечные (никаких перерисовок карты из-за смены темы).
- **React Query** — все серверные данные: ключ `['day', date]`, `['geo', 'control', date, lod]` и т.д. `staleTime: Infinity` для исторических дат (immutable), обычный TTL — только для последней даты.
- **URL** — сериализованное подмножество Zustand (дата, вьюпорт, слои) через собственный `urlState`-синхронизатор; back/forward браузера работает как навигация по датам.

### 3.2. Поток смены даты

```
setDate(next)
  → React Query: prefetch уже сделан? (да для соседних дат) → данные мгновенно
  → MapView получает {prev, next} геометрии
      → interpolateFrontline(prev, next, t)   // ресемплинг + lerp вершин
      → crossfade зон контроля (feature-state opacity)
      → diff-слой: gained (анимация подсветки), lost (красная пульсация)
  → EventsPanel/Stats/Charts перерисовываются из bundle.json
```

Предзагрузка: при выбранной дате D загружаются D±1; при воспроизведении — скользящее окно D+1..D+K (K зависит от скорости), уровень детализации — от скорости (см. улучшение №3).

### 3.3. Карта

- Один инстанс MapLibre на всё приложение (вне React-реконсиляции, через ref-обёртку).
- Слои данных — `GeoJSONSource.setData()` + `feature-state` для анимаций; тяжёлая подложка и детальные границы — PMTiles.
- Анимации — `requestAnimationFrame`-цикл с easing (не Framer Motion: он для DOM-панелей, не для WebGL-слоёв).
- Виртуализация панели событий — `@tanstack/react-virtual`.

## 4. Backend-архитектура (NestJS)

- Модули соответствуют доменам (days, events, geo, losses, charts, search, sources, export).
- Слои: Controller → Service → Repository (Prisma; для PostGIS-запросов — типизированный raw SQL в репозиториях `packages/db`).
- Валидация DTO — zod-пайпы из `packages/shared`.
- Кэш: Redis (ключ = нормализованный запрос; для исторических дат TTL = ∞ с инвалидацией по manifest-версии), плюс HTTP `Cache-Control`/`ETag` — CDN кэширует и API-ответы.
- Rate limiting и Helmet — стандартно; аутентификация нужна только для внутренних ETL/админ-эндпоинтов (bearer-токен сервисного аккаунта).

## 5. ETL-пайплайн

```
fetch (по источнику) → raw-archive (S3, immutable)
  → normalize (канонические сущности, zod)
  → reconcile (сопоставление событий между источниками, выставление confidence,
               фиксация конфликтов ОТДЕЛЬНЫМИ записями — ничего не сливается)
  → geometry pipeline (валидация ST_MakeValid, дельты, площади, упрощение 4 LOD)
  → publish (одна транзакция: снапшоты+дельты+события+потери+daily_stats;
             затем генерация статических файлов; затем обновление manifest.json)
```

- Запуск: cron 1×/сутки + ручной перезапуск; идемпотентность — по `(source, source_ref, date)`.
- Журнал импортов (`import_runs`) — статус, количество записей, ошибки, версия кода.
- Правки истории (ретроспективные корректировки источников) — новый publish дня с инкрементом версии в манифесте; CDN-файлы дня перезаписываются, клиентский кэш сбрасывается сменой query-версии из манифеста.

## 6. Кэширование (сводно)

| Слой | Что | Политика |
|------|-----|----------|
| CDN | дневные бандлы, GeoJSON, PMTiles, статика Next | immutable, версия в манифесте |
| CDN | ответы API (поиск не кэшируем) | s-maxage 5 мин |
| Redis | горячие API-запросы, временные ряды | TTL/∞ + инвалидация при publish |
| React Query | все данные клиента | staleTime ∞ для истории |
| Браузер | последние N дней воспроизведения | LRU в памяти + HTTP-кэш |

## 7. Наблюдаемость и DevOps

- Docker Compose для локальной разработки (postgres+postgis, redis, minio, api, web).
- CI (GitHub Actions): lint → typecheck → unit → интеграционные (testcontainers c PostGIS) → build → deploy.
- Мониторинг: Sentry (web+api), pino-логи, метрики публикаций ETL (успех/объём/аномалии: «площадь контроля изменилась > X км²/день» — алерт на ручную проверку).
- Окружения: dev / staging / prod; данные staging — подмножество (3 месяца).

## Самопроверка этапа 3

- *Единая точка отказа — publish*: транзакция БД атомарна, но статика пишется после; при падении между ними манифест не обновлён → клиенты не видят полусобранный день. Манифест — последний шаг, это и есть коммит-точка. ✔
- *Не переусложнён ли API при статике?* Нет: модули search/export/charts реально динамические; days/geo — тонкие обёртки над теми же данными для не-CDN сценариев и админки.
- *Риск: один инстанс MapLibre и React 18 StrictMode* (двойной mount в dev) — обёртка должна быть идемпотентной; отмечено как обязательный тест.
- *Слабое место: сверка событий между источниками (reconcile) — самая сложная логика проекта.* Решение: в MVP сверка полуавтоматическая (кандидаты на слияние по дате+гео+типу предлагаются, подтверждаются редактором), полная автоматика — после накопления статистики.
