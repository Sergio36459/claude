# Этап 6. Геоданные: форматы, хранение, анимация

## 1. Слои карты

| Слой | Формат доставки | Источник геометрии | Обновление |
|------|-----------------|--------------------|-----------|
| Подложка: границы, области, города, гидрография | PMTiles (векторные тайлы) | OSM + geoBoundaries/ГКНК | редко (месяцы) |
| Зоны контроля | GeoJSON на день, 4 LOD | DeepState (сверка с ISW) | ежедневно |
| Линия фронта | GeoJSON на день (2 LOD) | производная от зон | ежедневно |
| Диф за день (занято/освобождено) | GeoJSON на день | `ST_Difference` в ETL | ежедневно |
| Направления наступлений | GeoJSON на день | ISW (ручная разметка редактора) | ежедневно |
| События (точки) | из bundle.json → GeoJSON на клиенте | нормализация ETL | ежедневно |
| Военные объекты | GeoJSON (медленный слой) | только подтверждённые публичные | редко |

## 2. Формат GeoJSON (контракт)

Все файлы — `FeatureCollection`, WGS84, координаты с точностью 5 знаков (~1 м; больше не нужно, экономит ~30% веса). Обязательные `properties`:

```jsonc
// control.z{lod}.geojson — Feature на сторону
{ "type": "Feature",
  "geometry": { "type": "MultiPolygon", "coordinates": [...] },
  "properties": {
    "side": "ru" | "contested",         // 'ua' не рендерится полигоном (фон)
    "date": "2023-06-06",
    "areaSqkm": 108423.5,
    "sourceCode": "deepstate",
    "lod": 1
  } }

// frontline.geojson
{ "properties": { "date": "...", "lengthKm": 1248.2, "sourceCode": "deepstate",
                  "segmentId": 3 } }    // стабильные ID сегментов между днями — база интерполяции

// diff.geojson — Feature на связный полигон изменения
{ "properties": { "date": "...", "kind": "gained_ru" | "gained_ua",
                  "areaSqkm": 12.7, "oblast": "Донецька" } }

// axes.geojson
{ "properties": { "date": "...", "side": "ru", "label": "напрямок на Часів Яр" } }
```

## 3. Уровни детализации (LOD)

Генерация в ETL: `ST_SimplifyPreserveTopology` c допусками, подобранными по весу файла:

| LOD | Допуск | Назначение | Целевой вес зон контроля |
|-----|--------|-----------|--------------------------|
| z0 | ~2 км | playback ≥5x, мобильные, превью | ≤ 30 КБ |
| z1 | ~500 м | обзорный зум (страна целиком) | ≤ 150 КБ |
| z2 | ~120 м | региональный зум | ≤ 600 КБ |
| z3 | ~30 м | максимальная детализация | ≤ 2.5 МБ |

Клиент выбирает LOD по зуму и режиму (playback → принудительно z0/z1). Топология сторон согласована: упрощение применяется к общей линии границы (иначе при упрощении появятся щели между 'ru' и 'contested').

## 4. Хранение истории: снапшот + дельта

- **БД** (см. этап 4): keyframe-снапшоты (каждое воскресенье + первые дни крупных изменений), между ними `control_deltas`. Реконструкция дня: `keyframe ⊕ Σ deltas` (SQL-функция `rebuild_control(date, side)`).
- **CDN**: материализованные файлы на **каждый** день (реконструкция выполняется один раз в ETL, а не при каждом чтении).
- **Сырьё**: оригинальные файлы источников (GeoJSON/KML DeepState и др.) — в raw-архиве S3 навсегда: аудит и переигрывание пайплайна.

Оценка объёма: 1600 дней × (z0..z3 + frontline + diff) ≈ 1600 × ~3.5 МБ ≈ **5–6 ГБ статики** — тривиально для объектного хранилища, и лишь малая часть когда-либо скачивается одним клиентом.

## 5. Анимация смены даты (ядро UX)

Честный морфинг произвольных мультиполигонов (flubber и аналоги) нестабилен на геометриях фронта (тысячи вершин, меняющаяся топология, анклавы). Проектное решение — **трёхслойная композиция**, дающая визуально «плавную трансформацию» без топологических артефактов:

1. **Линия фронта — истинная интерполяция.** Сегменты с совпадающими `segmentId` ресемплируются до одинакового числа вершин (N по длине дуги), затем вершины лерпятся `P(t) = P₀(1−t·e) + P₁(t·e)` с easing в rAF-цикле (~300–500 мс на шаг дня; при playback — длительность = интервал кадра). Появившиеся/исчезнувшие сегменты — fade-in/out.
2. **Зоны контроля — кросс-фейд.** Два GeoJSON-сорса (prev/next); opacity через `feature-state` за то же окно анимации. Так как разница между соседними днями мала, кросс-фейд неотличим от морфинга, но стабилен всегда.
3. **Диф-слой — акцент изменения.** Поверх: `gained_ru` — красная пульсация (2 цикла, затем растворение в основной цвет), `gained_ua` — сине-жёлтая вспышка аналогично. Пользователь видит, *что именно* изменилось — это информативнее морфинга.

Fallback (слабое устройство / `prefers-reduced-motion`): шаги 1 и 3 отключаются, остаётся мгновенный кросс-фейд.

Реализация — `packages/geo` (ресемплинг, лерп, площадь) + `apps/web/lib/map-animation.ts` (rAF-оркестратор, очередь дат при playback: если пользователь листает быстрее анимации, промежуточные даты схлопываются до последней запрошенной).

## 6. Подложка (PMTiles)

- Сборка: OSM-экстракт Украины + соседние регионы → tippecanoe/planetiler → `base.pmtiles` (~200–400 МБ, зумы 0–12).
- Слои: admin-границы, населённые пункты (ранжирование по населению для зум-зависимых подписей), дороги (крупные), вода.
- Стиль: собственный JSON-стиль (light/dark варианты), подписи UK/EN по локали.
- Хостинг: тот же bucket + CDN; range-запросы, никакого тайл-сервера.

## 7. Пайплайн геометрии в ETL (порядок операций)

```
raw (DeepState GeoJSON) → ST_MakeValid → снап к границе Украины (ST_Intersection)
  → согласование топологии сторон → расчёт площадей (geography)
  → дельты к предыдущему дню (ST_Difference × 2, фильтр шума < 0.2 км²)
  → извлечение линии фронта (общая граница ru/ua) + segmentId-трекинг
  → 4 × ST_SimplifyPreserveTopology → запись БД → генерация GeoJSON-файлов → manifest
```

Фильтр шума важен: DeepState ежедневно двигает вершины на метры без смысловых изменений; без порога диф-слой будет мерцать мусором.

## Самопроверка этапа 6

- *Самый рискованный пункт — `segmentId`-трекинг линии фронта между днями* (фронт рвётся/сливается). Митигация: трекинг по пространственному перекрытию буферов сегментов (Hausdorff/overlap ≥ 60% → тот же id); при несопоставимости сегмент честно фейдится, а не «телепортируется». Прототипируется в первой итерации разработки (спайк недели 1), т.к. влияет на формат файлов.
- *Щели при независимом упрощении полигонов* — закрыто требованием упрощать общую границу (topology-aware, реализуется через `ST_Simplify` на топологии или упрощение линии фронта с восстановлением полигонов).
- *Пересчёт при ретро-правках источника*: правка дня X инвалидирует дельты X и X+1 и все производные файлы — publish умеет каскадное переиздание диапазона.
- *60x playback*: 60 дней/с × (z0 ≈ 30 КБ + diff ≈ 10 КБ) ≈ 2.4 МБ/с — реалистично на среднем канале; плюс прогрессивная предзагрузка и схлопывание очереди анимации. ✔
- Проверена альтернатива: хранить всю историю фронта одним тайлсетом с атрибутом даты (`history.pmtiles`) и фильтровать по дате в стиле — отложено в фазу 2 как оптимизация playback (меньше запросов), не как замена дневных файлов (нужны они же для диффов и bundle).
